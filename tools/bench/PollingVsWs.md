# 轮询 vs WebSocket 实时方案对比实验（EV-PERF-04）

> 目标：用同一台服务器、同一套发送节奏，对比「3 秒 REST 轮询拉群聊历史」与
> 「WebSocket 服务端推送」的**消息端到端延迟、单位时间 HTTP 请求数、接收字节数**，
> 为 `docs/SPEC.md` 第 4 节「实时方案」决策提供实测数据。
>
> 原始数据：[`assets/bench/polling_vs_ws.csv`](../../assets/bench/polling_vs_ws.csv)
> 工具：[`PollingVsWsMain.java`](PollingVsWsMain.java)、[`polling_vs_ws.sh`](polling_vs_ws.sh)

## 1. 方法

1. 注册两个用户：`sender`（发送者）与 `observer`（观察者）。
2. 发送者通过 WS 以固定节奏发送群聊消息：每 1 s 一条，共 30 s（30 条左右），内容带唯一序号
   `pollws-<ws|poll>-<时间戳>--<seq>`。
3. **WebSocket 场景**：观察者建立 WS 长连接；服务端每条消息实时推送。
   收到目标消息时用本地 `nanoTime` 计算延迟；统计收到的帧字节数、HTTP 请求数（0，仅 1 次 WS 握手）。
4. **3 秒轮询场景**：观察者不建 WS，每 3 s 调一次 `GET /api/messages/group?limit=200`，
   在响应里按序号识别新消息，用 `轮询响应时刻 - 发送者发送时刻` 计算端到端延迟；
   统计轮询请求数与每次响应体字节数。
5. 两个场景使用相同发送节奏、相同服务器（8081）、连续执行，取 P50/P95/Max 对比。

运行：

```bash
cd /home/versi/Projects/Java
source scripts/env.sh
tools/bench/polling_vs_ws.sh --duration 30 --send-interval-ms 1000 --poll-interval-ms 3000
```

## 2. 结果（2026-11-18，16 核/30 G，同机环回）

| 场景 | 消息数 | 平均延迟 | P50 | P95 | 最大延迟 | HTTP 请求数 | 接收字节 | 每消息字节 |
|---|---|---|---|---|---|---|---|---|
| **WebSocket 推送** | 31 | **34.46 ms** | 10.16 ms | **327.37 ms**\* | 416.07 ms | **0**（2 次 WS 握手） | **6.2 KB** | 199.7 B |
| **3 s REST 轮询** | 27 | **2005.15 ms** | 2005.14 ms | **3006.03 ms** | 3006.88 ms | **9 次 / 30 s（18 次/分钟）** | **212.7 KB** | 7 877.8 B |

\* 采集时机器后台有其它进程负载（load≈3–5），WS P95 偏高；空载单连接实测 P50 约 1.5–10 ms。
轮询 P50≈2.0 s、P95≈3.0 s 与其 3 s 轮询周期吻合（平均需等半个周期）。

## 3. 结论

1. **延迟**：WS 平均延迟 34.46 ms vs 轮询 2005.15 ms（低约 **58 倍**）；P95 327.37 ms vs 3006.03 ms（低约 **9 倍**）。
   轮询的延迟下界由轮询周期决定，无论服务器多快都至少有 0～3 s 的固有延迟。
2. **请求数**：30 s 内轮询 9 次 HTTP 请求（18 次/分钟），WS 0 次 REST 请求（仅 1 次握手）。
   用户越多、轮询越密，REST 压力线性增长；WS 请求数与用户数无关。
3. **带宽**：轮询每次返回最近 200 条历史（响应体约 23.6 KB/次），30 s 共 212.7 KB；
   WS 只推增量消息，共 6.2 KB。轮询接收字节约为 WS 的 **34 倍**（每消息 7 877.8 B vs 199.7 B），
   且随历史消息数增长。
4. **代价**：WS 需要维护长连接、心跳（10 s ping / 35 s 超时）与断线重连（指数退避）；
   轮询实现简单、无长连接状态。对本项目「局域网内 500 并发在线聊天」场景，WS 的延迟/请求数/带宽优势显著，
   与 `docs/SPEC.md` 方案论证一致。

## 4. 备注

- 服务端无 `POST /api/messages` 接口（消息只允许走 WS），因此轮询场景的「发送」仍由 WS 完成，
  对比的是**接收侧**的实时性与请求开销，与实际「轮询拉历史」的前端方案一致。
- 轮询场景统计 27/31 条：最后几条消息发送于最后一轮轮询之后，实验窗口内未被拉到，
  属正常边界（不影响延迟分布与量级结论）。
