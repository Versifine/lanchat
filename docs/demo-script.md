> 用途：课程报告当堂展示 / 答辩式演示。总时长 5:00，含演示前准备清单、逐段台词与操作、应急方案、老师可能提问的回答。

## 2. 逐段台词与操作

### 0:00–0:20 开场

**操作**：站定，指向两个浏览器窗口。

**台词**：
"老师好，我是计算机科学与技术 24-4 班的（姓名）。我的课程项目是 **LanChat 局域网聊天室**——一个可以直接在浏览器里用的即时通信系统。左边这个窗口是爱丽丝，右边无痕窗口是鲍勃，两个账号连的是同一个服务端，接下来我用五分钟演示它，并说明它背后的设计。"

---

### 0:20–0:55 登录页与视觉风格

**操作**：先指着 A 窗口登录页（如已登录则退出，或直接讲 B 窗口登录页）。

**台词**：
"登录页采用前后端分离的 B/S 架构：浏览器里是 Vue 3 + Element Plus 的单页应用，服务端是 Java 21 + Spring Boot 3.5。视觉上我选择了偏国外独立网站的编辑排版风格：纸张底色、墨色文字、1 像素细线、衬线标题配等宽标签，**没有使用彩色渐变和大色块**，重点让内容自己说话。表单有用户名、密码格式校验和提交防重复。"

**操作**：在 A 窗口输入账号密码 → 点「LOG IN / 登 录」→ 进入聊天主界面。

**台词**："登录成功，进入聊天主界面。"

---

### 0:55–2:05 群聊双端实时（重点 1）

**操作**：在 A 窗口输入框输入："大家好，我是爱丽丝，今晚一起对课程报告。" 回车发送。

**台词**：
"这是群聊。消息发出去后，服务端会先落库、再广播给所有在线用户——注意右边鲍勃的窗口**实时**收到了同一条消息，并且两边都显示服务端统一的时间戳。发送者能看到自己的消息回显，说明服务端确实受理了。"

**操作**：在 B 窗口（鲍勃）发："收到！我这边测试已经全部通过。" 回车。

**台词**：
"反向也一样。左侧是在线用户列表和未读提示：谁在线用绿色小圆点表示，点击某个用户可以进入私聊，未读消息会出现计数红点。"

**操作**：指着左侧栏与顶部 `ONLINE 2`。

**台词**：
"顶栏的 ONLINE 2 和状态灯来自 WebSocket 的实时推送；断线时这里会变成断开状态并提示重连，这部分我在测试里专门验证过。"

### 2:05–2:45 私聊 + 离线补发

**操作**：在 A 窗口点击左侧「鲍勃」→ 进入私聊 → 输入："那个并发注册的 BUG 你们后来怎么修的？" 发送。

**台词**：
"私聊只推送给对话双方，不广播给其他人。服务端先查会话、再落库、再定向推送给接收方；如果接收方当时不在线，消息会入库等对方下次登录时补发，标识为 offline=true，只补发一次。"

**操作**：指向 B 窗口，鲍勃收到私聊。

**台词**："两边看到的是同一个服务端消息 ID 和顺序，前端不做乐观发送，避免本地回显和服务端回显重复。"

### 2:45–3:30 文件传输（重点 2）

**操作**：在 A 的私聊/群聊输入区点回形针图标 → 选择 `report/figs/fig-05-01-architecture.png` → 发送。

## 3. 应急方案

| 故障 | 处理 |
|---|---|
| 服务端起不来 / 端口被占 | 换端口：`java -jar backend/target/lanchat-backend.jar --server.port=8082`，浏览器开 :8082 |
| 一个浏览器窗口卡住 | 用另一个窗口继续讲，或刷新页面（自动重新登录态丢失，用演示账号重登） |
| 文件选择框不方便找路径 | 提前把 `fig-05-01-architecture.png` 复制到桌面或下载目录 |
| 网络/投屏异常 | 打开 `assets/screenshots/final-*.png`（登录/群聊/私聊/文件/暗色各一张）按截图讲，效果几乎一致 |
| 现场要求演示"断线重连" | 可选：终端 Ctrl+C 停服务 → 5 秒内重启 → 两个窗口出现"连接断开，正在重连…"→ 自动恢复。操作前先说"这是破坏性演示" |
| 时间不够 | 砍掉 3:30–3:50 暗色模式一段，直接进架构；台词不变 |

## 4. 老师可能提的问题与应答（背 3–5 条即可）

**Q1：为什么用前后端分离？为什么不做桌面/小程序？**
A：老师验收和现场展示零安装，浏览器打开就能用；前后端分离也是主流工程实践。代价是服务端和客户端不能共享代码，靠 `docs/api.md` 作为唯一契约保证两边一致；报告里专门写了这一点。

**Q2：AI 写了多少？你做了什么？**
A：AI agent 按我写的规格和评测集实现代码、测试与文档；我负责需求分析、SPEC/契约、验收门禁和关键决策（两次方案回调、缺陷修复取舍、演示与报告）。过程记录在 `docs/ai-devlog.md`，包括人工审批和两次"回需求重定义边界"。

**Q3：性能数据怎么来的？可信吗？**
A：用 JDK 自带 HttpClient 写压测客户端，全新数据库的独立实例，500 连接、渐进建连、`-Xmx512m`，原始 CSV 在 `assets/bench/`，报告 7 章有环境、参数与瓶颈分析。局限也如实写了，不夸大。

**Q4：安全做了什么？**
A：JWT 鉴权、PBKDF2 加盐密码哈希、SQL 全部 PreparedStatement 参数化、消息按纯文本渲染防 XSS、上传文件名清洗防目录穿越、消息/登录限流、日志不打印密码与完整 token；有对应的自动化安全用例。

**Q5：SQLite 能撑住吗？**
A：WAL + 短事务下，压测中 1000+ 消息/秒持续写入没有出现锁错误，500 连接稳定；真正的瓶颈不在 SQLite，而是建连高峰时"全量 userList 广播"的 O(N²) 和广播 O(N) 扇出——下一步计划改成增量/合并推送与异步广播队列。

**Q6：界面为什么没有颜色、挺朴素的？**
A：这是我选定的编辑排版风格（editorial indie）：纸色、墨色、细线、单一强调色，去掉渐变和装饰，让信息层级靠排版而不是颜色；深色模式同一套语言。
